# 128K 输入 Prefill / Decode 速度对比（DSA vs 固定分块 HISA vs Adaptive-HISA）

日期：2026-09-21，机器 h20-9-57（8×H20，TP8），模型 DeepSeek-V3.2（`/workspace/qyl/models/deepseek-v3.2`）。
原始数据：`/DATA/disk0/qyl/data/speed_bench_20260921/<arm>/results.jsonl`，`server.log`，`launch.json`。
脚本：`/tmp/hisa_speed/run_arms.py`（启停容器）、`/tmp/hisa_speed/bench_client.py`（流式客户端）。

## 测量方法

- 输入：固定随机 `input_ids`（seed 20260920，128K = 131072 token），输出 128 token，`temperature=0, ignore_eos`。
- 每个 arm 单独起一个 `sglang.launch_server` 容器（同一镜像 `qyl/sglang-hisa:eval`），跑完即停；GPU 上没有其他进程。
- 1 次 warmup + 3 次正式测量，取中位数（三次之间波动 < 0.02 s / 0.1 ms）。
- TTFT = 客户端发出请求到收到第一个 token 的时间（`stream=True`），包含 HTTP、调度、全部 16 个 8192-token chunk 的 prefill。
- TPOT = (最后一个 token 时间 − 第一个 token 时间) / (128 − 1)。
- 服务器参数（三者相同）：`--tp-size 8 --context-length 163840 --chunked-prefill-size 8192 --mem-fraction-static 0.82 --max-running-requests 1 --disable-radix-cache`；
  `graph` 列为 `--cuda-graph-bs 1`，`nograph` 列为 `--disable-cuda-graph`。
- `SGLANG_NSA_FUSE_TOPK=0`（与精度 e2e 一致）。

三个 arm：

| arm | 代码 | 说明 |
|---|---|---|
| DSA | `sglang_hisa/python`（`f716c41a0`，官方 DSA indexer，默认 `use_hisa=false`） | 密集 indexer：每个 query 对全部 key 算 logits，Top-2048 |
| HISA-64 | `sglang_hisa_fixed_e399d9f/python`（`e399d9f33`，固定分块 HISA） | `use_hisa=true, hisa_k_block_size=64, hisa_block_topk=128`：64-token 固定块均值做粗筛，每 query 选 128 块 = 8192 候选 token，块内精排 Top-2048；prefill 与 decode 都走两级 |
| Adaptive（ours） | `adaptive_0921_h201/python` | P-key 自适应分区（L/8 λ-DP split → L/64 target merge，`key_sse`），decode 走 summary 粗筛 + 8192 候选 + 精排；**prefill 仍是官方密集 DSA indexer**（最后一个 chunk 顺带在 side stream 上建分区） |

Adaptive 环境：`MODE=adaptive_decode, PARTITION_METRIC=key_sse, SPLIT_BACKEND=gpu, MERGE_POLICY=sync_nonoverlap, MERGE_TARGET_DIVISOR=64, MERGE_TARGET_ROUNDS=8, GRAPH_BUILD=1, GPU_STREAM=side, SINK=64, TAIL=256, CANDIDATE_TOKENS=8192, DECODE_CHUNK=64, SKIP_CLEAN=1, FUSE_PAGE_TABLE=1, RAW_FP8_BUILDER=1, LAMBDA_MAX_ROUNDS=6（默认）`。

## 解读

1. **Decode 必须看 CUDA-graph 列。** 不开 graph 时三者 TPOT 都在 200 ms 以上，且 32K/64K/128K 完全相同（adaptive 32K 213.8 / 64K 213.4 / 128K 212.9 ms），说明整个 decode 步被 CPU 发射 ~万级 kernel 的开销主导，与注意力算法无关。开 graph 后回到 18–20 ms。
2. **Adaptive decode 比 DSA 快 5.4%（19.2 vs 20.3 ms），比 HISA-64 慢 1.4 ms。** 一步 decode 中 indexer 只占一小部分（61 层 × ~50 µs 级别），三者的差别主要是 indexer 部分：DSA 每层对 128K key 算 logits + Top-2048；adaptive 是 summary 粗筛（~2K 行）+ 8192 候选精排；HISA-64 同样两级但块结构固定、kernel 融合度更高（无 leaf 展开、无 seal）。
3. **TTFT：adaptive 与 DSA 几乎相同（+0.5 s），HISA-64 快 30 s。** 当前 adaptive 的 prefill 索引仍是密集 DSA（每个 8192-query chunk 对全部前缀 key 算 `[8192, N]` logits），128K 时这部分大约占 prefill 一半的时间；HISA-64 的 prefill 走两级稀疏索引，所以省了 ~30 s。+0.5 s 是最后一个 chunk 上 61 层分区构建（side stream，与模型计算重叠）以及 forward 末尾等待合流的代价。
4. 因此下一步（adaptive_0921_h202 正在做）：把 adaptive 的两级选择搬到 prefill——每个 chunk 顺带对已 seal 的前缀建分区，下一个 chunk 的 indexer 用 summary 粗筛 + 叶子展开 + 因果局部窗口 + 精排 Top-2048 代替密集 logits。单层单 chunk 微基准（真实 dump，N=73K，8192 query）：稀疏 39 ms vs 密集 113 ms；对前缀部分的 Top-2048 recall 与 HISA-64 均值 summary 持平（0.597 vs 0.597）。

## 追加（2026-09-21 22:17–22:29）：prefill coarse 选 chunk 改为 batched weighted radix select

改动（`adaptive_0921_h202`，`adaptive_hisa/prefill_select.py` + 新增 `csrc/prefill_weighted_select.cu`）：
原来每个 2048 行子批 `torch.argsort(coarse) → cumsum(leaf_len) → _expand_slots_kernel`（每个输出 slot 对 incl 前缀做 log2(叶数) 次二分），
改为一个 CUDA 算子：每个 query 行一个 CTA，把 decode `weighted_select` 的 token 加权 4 轮 radix 阈值搜索批量化
（叶子 key/长度放 shared memory；每轮 256-bin 加权直方图 + block 前缀和定位越界 bin；逻辑序打包 64-bit 前缀和得到每叶 taken/输出偏移并压缩被选叶；
一个 warp 写一个被选 interval 的连续 token；可选输出 `(start, length, output_offset)` 段）。
选出的 token 集合与旧路径完全一致（同分并列改为叶下标升序；单测 `TestWeightedSelect` + 原 `sparse_topk_core` 端到端单测均通过）。
旧路径保留：`SGLANG_NSA_ADAPTIVE_HISA_PREFILL_SELECT=argsort`。

## 追加（2026-09-21 23:20–23:32）：精排 kernel 改走 HISA 持久化 block-sparse kernel；SSE 树跨 chunk 增量构建

### 先量化：128K 最后一个 chunk（8192 query）prefill indexer 每层各阶段（H20 单卡，`fine_scorer_stage_bench.py`，合成数据）

| 阶段 | 时间 (ms) | 说明 |
|---|---:|---|
| coarse GEMM `[8192 × 1920]` summary | 1.34 | |
| weighted select（选叶 + 展开 8192 token） | 0.53 | 上一节的新算子 |
| **fine：`sparse_paged_mqa_triton` K=1（原）** | **5.27** | 8192 行 × 8192 候选 × 64 头 × 128 维 = 1.1 TFLOP → **209 TFLOPS** |
| fine：HISA `block_sparse_mqa_triton` **K=64**（128 个对齐块，同样 8192 token） | 5.58 | 连续块并不更快 |
| local window 密集 GEMM `[8192 × 8192]` 因果 | 2.37 | DeepGEMM |
| cat + Top-2048（16K 候选） | 2.09 | `hisa_topk_candidates_fused` |
| （参照）密集 DSA logits `[8192 × 131072]` | 66.7 | 264 TFLOPS，DeepGEMM |

结论：**精排在 H20 上是算力瓶颈，不是访存/索引瓶颈。** H20 fp8 dense 峰值约 296 TFLOPS，原 K=1 kernel 已到 71%，
HISA 自己的 K=64/GROUP_SIZE=4/GEMM_TILE=256 kernel 处理同样多的 token 反而慢 6%。原因：每个 fp8 key 行正好是一条 128 B cache line，
按 token gather 和按 64 块连续读的 DRAM/L2 事务数相同；K=64 省下的只是每 token 的 page-table 查找和地址运算，而这些都不在瓶颈上。
所以"让精排知道 64 个 token 属于同一个 leaf"本身省不出时间；能省的是 FLOP（候选数）或 kernel 的 tensor-core 效率。

### 改动 1：精排改为 HISA 持久化 kernel（flat index-K，K=1）

`hisa/triton_kernels.py::block_sparse_mqa_triton` 增加 `kv_block_size=1`（候选表直接是 token id，允许 -1 填充），
`prefill_select._fine_scores` 在有 `k_flat`（密集路径已 gather 好的 `[N,128]` index-K）时走它：一个 CTA 负责一行的 2048 个候选，
Q 只读一次，`[64,128]` fp8 tile，下一步的 gather 与本步 GEMM 重叠（`num_stages`），不再查 page table。配置扫描（`fine_scorer_flat_sweep.py`，
2048 行 × 8192 候选，候选为 128 段连续 64-token 区间）：

| 配置 | ms / 2048 行 |
|---|---:|
| 原 `sparse_paged_mqa_triton` K=1（paged，每 64 token 一个 program） | 1.35 |
| flat 持久化 G=64 KC=32 warps=4（**采用**） | **1.106** |
| flat 持久化 G=128 KC=16 warps=4 | 1.23 |
| flat 持久化 G=256 KC=32 warps=8（HISA K=64 的默认形状） | 1.47 |

采用配置 = **249 TFLOPS（fp8 峰值的 84%，与 DeepGEMM 密集 GEMM 的 89% 相当）**，每 chunk 精排 5.4 → 4.4 ms。分数与原 kernel 逐位相同（同一 fp8 dot，单测断言 `torch.equal`）。

### 改动 2：Key-SSE 树跨 chunk 增量构建（`TREE_CACHE=1`，默认开）

dyadic 节点不跨 root（256 token），所以已 seal 前缀 `[0, n_old)` 内每个节点的 `sum(K)`/`sum(K²)`/SSE 在更长前缀的树里完全不变，
只有 level 偏移变化。`partition_kernels.raw_fp8_tree_triton_incremental`：把旧树各 level 拷到新树对应位置（一个 kernel），
`_fp8_chunk_tree_kernel`/`_fp8_upper_tree_kernel` 只对新增 root 启动（新增 `c0`/`r0` 偏移参数）。`prefill_runtime._TreeCache` 按 `(layer, req)`
带 epoch 缓存上一 chunk 的树，最后一个 chunk 用完即释放（16 B/token/层）。λ 搜索、Split、Merge 仍在整棵树上做（M0、λ、merge target 都随长度变）。

| 前缀 N | 整棵重建 (ms) | 增量 +8192 token (ms) |
|---:|---:|---:|
| 16K | 0.167 | 0.102 |
| 64K | 0.606 | 0.095 |
| 128K | 1.194 | 0.096 |

结果与整棵重建**逐位相同**（`tree_incremental_bench.py`，atom/root ∈ {1/256, 8/256, 1/64, 4/128}，16 个 chunk 链式验证；单测 `test_incremental_tree_is_bitwise_identical`）。
但整个 partition build 每 chunk 的 GPU 时间（`partition_build_bench.py`，CUDA graph 回放测纯 GPU 时间）：16K 1.5 ms、64K 2.7 ms、128K 4.7 ms，
其中 tree 只占 0.2–1.2 ms，**merge 8 轮约 2.7 ms 且与 N 无关（latency-bound 小 kernel）**，dp+repair 约 0.7–1.0 ms。建树并非 build 的大头。

## 追加（2026-09-22 00:25–00:31）：decode 选择算子 `weighted_select.cu` fast path 优化（TPOT 19.16 → 18.10 ms）

参考 `Adaptive_HISA_WeightedSelect_Warp优化_Cursor修改指南.pdf`。所有改动对 `selected_prefix / count / candidates` 逐元素等价于精确 6-pass legacy kernel
（`test_weighted_selector_fast_path_bit_exact_sweep`：n = 0/1/31/32/33/1023/1024/1025/4096、并列分数、±0、极小/极大、长度 0 / guard 截断 / crossing leaf、
budget 小于 guard / 大于全部、60 组生产形状随机、CUDA graph 回放）。

### 单算子微基准（H20 单卡，`runner/bench_weighted_select.py`，adaptive_real 叶长，budget 8192，中位 µs）

| n（叶子数） | 旧 full（prefix+expand） | 新 full | 加速 | 旧 prefix kernel | 新 prefix kernel | 旧 expand | 新 expand | HISA `fast_topk` |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1024 | 31.3 | **11.5** | 2.7× | 22.4 | 8.9 | 8.9 | 8.2 | 10.1 |
| 2048 | 38.8 | **14.2** | 2.7× | 23.6 | 10.1 | 15.3 | 8.5 | 10.1 |
| 4096 | 52.9 | **19.3** | 2.7× | 25.4 | 14.4 | 27.6 | 8.6 | 10.1 |

三项改动及各自贡献：

1. **PDF 的两项 warp 优化（Phase A/C `__match_any_sync + __reduce_add_sync` 聚合 histogram 原子；Phase B ballot 压缩 threshold bucket）**：
   已实现，编译期位掩码 `ADAPTIVE_HISA_WS_WARP_OPT`（env `ADAPTIVE_HISA_SELECT_WARP_OPT`，1/2/4 分别对应 A/B/C，`7` 全开），
   逐位等价。但在 H20 上**都不是收益**：Phase A +2.6 µs、Phase C +1.7 µs、Phase B ±0（n=1024，n=4096 更差；
   正分数集中分布 `--scores relu` 结论相同：mask=7 时 prefix 8.9 → 10.9 µs）。单 CTA 1024 线程对 ~10–25 个热 bin 的 shared 原子本身很便宜，
   `__match_any_sync` 的逐唯一值循环反而更贵——这正是 PDF 风险清单里"优化后更慢"的情形。默认 0（逐叶原子）。
2. **真正的热点：单线程 256-bin 倒序扫描找 threshold byte**，每次 ~3.5 µs 的串行 shared 依赖读，Phase A + Phase C 三轮共 4 次 ≈ 14 µs。
   改为 `warp_threshold_bin`（一个 warp、每 lane 8 个 bin、shuffle 前缀 + ballot），结果相同：prefix kernel 22.4 → 8.9 µs（n=1024）。
3. **`expand_selected_kernel`**：原来每个 warp 一次只看一个 leaf（每 warp n/32 次依赖全局读）。改为每 warp 每轮 32 个 leaf 合并读，
   ballot 逐个展开选中的区间：15.3 → 8.5 µs（n=2048），27.6 → 8.6 µs（n=4096），与 n 无关。

## 追加（2026-09-22 00:57–01:09）：Top-K 直接读两段 logits（去掉 `torch.cat`）；chunked-prefill-size 4096 对比

### 改动：`hisa_topk_fused.cu : topk_candidates_split_kernel`（`hisa_topk_candidates_split`）

原来每个 2048 行子批要 `torch.cat((fine_leaf [R,8192], local [R,≤8448]))` 和 `torch.cat((cand_leaf, local_ids))`
（fp32 + int32 各 ~134 MB 读写）再喂 HISA 的 radix Top-K。现在 radix 选择器通过 `SplitRow`（列 `r < 8192` 读叶子 logits，
否则读局部窗口 logits `r − 8192`）就地读两段，候选 id 同理（`r < 8192` 查 `cand_leaf`，否则 `n_complete + r − 8192`），
不再物化拼接，也不再需要 −inf pad。`fast_topk_cuda_tl` 改为模板以接受该行视图，HISA 原有 kernel 不受影响。

`fine_scorer_stage_bench.py`（128K 最后一个 chunk，8192 query，H20 单卡）：cat + topk 2.087 ms → split topk **1.272 ms**（−0.8 ms/层/chunk）。
选中集合与旧路径一致（`test_split_topk_equals_fused_topk_on_concatenation`：与 cat 版和精确 `torch.topk` 逐行集合相等，
含 ke 落在窗口内、窗口为 strided 切片、有效列 < 2048 的行）。注意 HISA 的 radix Top-K 在阈值处用原子解 tie，同一输入两次运行
也可能在个别并列 token 上不同，所以对照要按集合比。

同时清理了 `sparse_topk_core` 里对已连续张量（行切片）的冗余 `.contiguous()`（它们是 no-op，不产生拷贝，只是噪音）。
